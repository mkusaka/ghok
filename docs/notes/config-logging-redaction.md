# Config, logging, and redaction

## Configuration

- `Dir(env)` uses nonempty `GHOK_CONFIG_DIR`, then `XDG_CONFIG_HOME/ghok`, then `HOME/.config/ghok`. Environment lookup uses the supplied map, not the process environment. `DefaultPath` appends `config.yaml`.
- `Load` supplies defaults for a missing file and stores its absolute containing directory in `Config.Dir`. Nonempty YAML requires `version: 1`; empty files, comments, null documents, and empty mappings use version 1. Explicit numeric zero limits remain errors. Only one YAML document is accepted. User config uses yaml.v3 `KnownFields(true)` to reject unknown fields with line numbers; project decoding ignores unknown top-level/nested fields and reports their paths as notes, including YAML merges/aliases. `Validate` joins independent validation failures with indexed field paths.
- Defaults are exported constants: observe mode; unknown mutation and unknown input audit; protected unknown deny; hooks enabled, timeout 10s (maximum 10m), pre onError deny, post onError ignore, maxOutputBytes 1 MiB; runtime concurrency 1, stdin/file limit 8 MiB, stdin timeout 3s, capture limit 1 MiB, resolve timeout 2s; logging enabled, info level, `logs/ghok.jsonl` beneath Config.Dir.
- Hook and rule IDs must be unique; hook dependencies must exist, have the same phase, and form an acyclic graph. Post hooks cannot deny on error; only post hooks can capture output. Match globs use `path.Match` syntax; repository patterns require owner/name shape.
- `policy.unknownInput` handles `input-unavailable`/`input-too-large` (including stdin timeout) separately from readable requests governed by `unknownMutation`. It accepts allow/audit/deny; explicit project values can only tighten it. Denial reasons retain the input failure cause.
- A rule's `onUnresolved: deny|ignore` defaults to conservative matching (`deny`); `ignore` skips that rule's unresolved repository/host maybe-matches, not other rules or protected-target handling. Nonempty ambiguous target candidates remain unresolved. Explain and hooks-test JSON carry `matched conservatively (target unresolved)` for deciding maybe-matches.
- `config validate` and `doctor` warn for each rule/active or ignored hook operation pattern matching no known action, using `normalize.KnownActionPattern`; obsolete exact names such as `issue.comment` warn while curated and generated action globs remain valid. Warnings do not invalidate an otherwise valid configuration.
- `HookCommandPath` resolves relative executable paths containing `/` against Config.Dir; bare names remain PATH lookups. Command arguments are unchanged.
- `LoadEffective` walks upward from the symlink-resolved cwd to the nearest `.git` file/directory, stopping before checking HOME or at the filesystem root. A HOME dotfiles repository is never a project root. Only that repository's `.ghok.yaml` is considered. Read, parse, validation, manifest, and effective-merge failures discard only the project contribution, retain the user config, and return notes plus `Config.Diagnostics` for invocation logging.
- Only explicitly supplied project policy values participate in tightening: observe < enforce and allow < audit < deny. Rules and protected repositories append; attempted weakening is ignored with a note. Any project runtime or logging section is an error, including empty sections and merged YAML keys. `trust.include` is project-only; user `trust.projects` is unsupported. Active hook/rule collisions invalidate the project overlay. Merging into a config copy prevents partial project changes escaping on validation failure.
- Invalid user errors retain raw YAML `policy.mode` independently of strict decoding/validation. `FailClosed(err, env)` rejects invalid raw-enforce configs and, with `GHOK_FAIL_CLOSED=1`, every invalid config including project files; observe or undeterminable mode otherwise fails open. Validate/doctor report the applicable behavior. Missing user config remains valid.
- Project hooks activate when a content digest matches the retained digest set in `<config-dir>/trust.json`. The v1 canonical manifest sorts unique repository-relative paths and encodes path NUL executable-bit NUL SHA256 content hash/missing marker. It includes exact `.ghok.yaml` bytes, root-contained hook executables and project `trust.include` files. Covered byte/exec-bit changes and creation of missing files revoke trust for that content; notes name changed files. Location is excluded, so identical content remains trusted across versions, worktrees and clones. Policy-only configs skip manifest computation.
- Each digest records `firstPath`, `configPath`, `trustedAt`, hook IDs and per-file executable bits and hashes/missing markers. Paths are diagnostic metadata, not digest inputs. `Config.Hooks` contains active hooks; `Config.IgnoredHooks` identifies untrusted or changed-since-trust hooks.
- `TrustProject(path, cwd, env)` validates repository-root `.ghok.yaml`, project restrictions and effective config, writes the record, and returns canonical path, enabled hooks with resolved commands, and notes naming every hashed file and coverage limits. `UntrustProject(path, cwd, env)` idempotently removes only the current digest, preserving other versions. Both reject missing configs/non-repository-root paths; empty path selects the current root.
- `ListProjectTrust(env)` backs `ghok config trust --list`: sorted digest, first path, trusted timestamp, hook IDs, per-file executable bit and hash/missing metadata, plus store notes. `UntrustAllProjects(env)` backs `ghok config untrust --all` and clears every digest, returning store notes. Policy remains active.
- Trust writes use a 0700 config directory and 0600 temporary file plus atomic rename to `trust.json`. Invalid or old-format stores return a generic note and grant no hook trust, without suppressing project policy.
- Project commands require `./relative` or absolute executable paths; user hooks retain bare PATH names. Relative paths resolve under the repository root; manifest files and symlink targets must stay inside it and be regular files. At most 256 files and a global total of effective `runtime.fileMaxBytes` are allowed. Absolute external executables are not hashed. Interpreters, PATH tools, unlisted imports, dependencies and data are not covered; add repository-relative dependencies/data via `trust.include` (for example `.github/scripts/check-pr-description.ts` and `.gitleaks.toml`).
- Group/world-writable config and hook files produce notes. Bare hook names are inspected through the supplied PATH; missing executables are left for the runner/doctor. Packages return notes without printing them; validate/doctor/explain present them, while ordinary wrapper stderr stays quiet.
- Hooks are explicitly trusted code. Trust/path hashes and atomic writes are not a security boundary against concurrent filesystem replacement, competing writers or direct GitHub API access.
- Schemas use the local standard-library reflection generator. Curate `types.go` tags and templates, not generated JSON; regenerate with `go generate ./internal/config`. No new upstream snapshot or generator dependency is needed.

## gh aliases: verified source behavior

Read-only source verification against [cli/cli v2.102.0 `internal/config/config.go`](https://github.com/cli/cli/blob/v2.102.0/internal/config/config.go): `NewConfig` delegates reading to cli/go-gh; `AliasConfig.Get/All` read the top-level aliases map without expanding it. [cli/cli v2.102.0 `go.mod`](https://github.com/cli/cli/blob/v2.102.0/go.mod) pins cli/go-gh/v2 v2.16.1. [cli/go-gh v2.16.1 `pkg/config/config.go`](https://github.com/cli/go-gh/blob/v2.16.1/pkg/config/config.go) verifies `ConfigDir` precedence and `generalConfigFile` naming.

`LoadGhAliases` reads `config.yml` from GH_CONFIG_DIR > XDG_CONFIG_HOME/gh > HOME/.config/gh. Missing files yield an empty map. Plain and `!`-prefixed shell aliases are preserved verbatim; expansion/shell classification is the normalizer's responsibility. Unrelated gh configuration keys are accepted. This reader does not read credentials from hosts.yml or the OS keychain, write gh configuration, or invoke gh.

## Secret redaction

- `New(env)` snapshots nonempty GitHub credential values (GH_TOKEN, GITHUB_TOKEN, GH_ENTERPRISE_TOKEN, GITHUB_ENTERPRISE_TOKEN). Other environment names containing TOKEN, SECRET, PASSWORD, PASSWD, API_KEY, PRIVATE_KEY, or CREDENTIAL contribute values only when at least eight bytes long.
- All learned values match anywhere. Pattern coverage includes classic GitHub token prefixes with at least 36 suffix characters, github_pat_, v1. plus 40 hex characters, JWT-like eyJ tokens, Bearer/token/Basic authorization values, Authorization/Proxy-Authorization headers, URL passwords, and complete or unfinished PEM private-key blocks.
- Marker: `[REDACTED]`. In the pathological case that a learned credential is part of the marker itself, the marker is scrubbed too; credential removal takes precedence over retaining that literal marker. Longest-first replacement and a terminating removal pass prevent overlapping or newly joined secret values from surviving.
- Sensitive names: token, accessToken, refreshToken, idToken, authToken, ghToken, githubToken, ghEnterpriseToken, githubEnterpriseToken, password, passwd, secret, clientSecret, apiKey, privateKey, credential, credentials, authorization, proxyAuthorization. Matching ignores ASCII case, underscores, and hyphens; bracket/dotted field paths inspect components. `key`, `keyboard`, `tokenizer`, and `publicKey` are not sensitive names.
- `Argv` handles separate/attached/equals header and API field flags, API boolean shorthand bundles, --password/--token and other sensitive-name flags, and `secret set --body/-b`. `variable set` bodies remain ordinary data. `auth login --with-token` has no argv token to redact. `--` ends contextual flag interpretation; learned-value/pattern redaction still applies to every string.
- `Value` copies JSON-like maps/slices, including common typed containers and JSON byte bodies. Numeric `json.Number` values retain their precision/type. `Result` and `Input` copy every mutable contract field and redact every string, including errors, metadata, URL credentials, and resolved context.
- GraphQL redaction uses gqlparser ASTs to scrub sensitive argument/input/default values and learned/pattern strings. Display copies are reformatted and comments omitted. Malformed/truncated GraphQL is withheld rather than emitted unparsed. These copies are never execution/replay input.
- Captured hook bodies are decoded, redacted, and re-encoded; JSON decoding preserves numeric precision. Invalid base64 or malformed structured bodies are withheld. Original byte-count/truncation metadata remains execution metadata.
- Unsupported: arbitrary application structs/pointers, cyclic non-JSON graphs, and credentials in unrecognized encodings. Ordinary binary bodies retain their nonsecret bytes. Redaction cannot infer arbitrary sensitive values under ordinary field names when they were neither learned nor pattern-shaped.

## JSONL logging

- API: `Open(path, level)`, `OpenWithRedactor(path, level, redactor)`, `Write(Record)`, `Close`, and `NewInvocationID`. Open and a nil injected redactor snapshot the process environment. Logger.Write always redacts a copy; callers need not remember a separate redaction step.
- Record fields use lowerCamelCase JSON. Zero timestamps become current UTC. Invocation IDs are crypto/rand 128-bit lowercase hex strings.
- A log directory created by ghok gets mode 0700; a pre-existing directory is left untouched (it may be shared). Log and persistent `.lock` files are 0600. Symlink final directories/log/lock files and nonregular files are rejected. Ancestor symlinks are permitted (including macOS /var and /tmp aliases).
- A mutex serializes each Logger's goroutines; flock on the persistent `<path>.lock` serializes cooperating processes. The append file is reopened under that lock so rotation cannot leave writers using stale data descriptors. Each JSON record plus newline uses one append write syscall. Never remove the lock file while writers may exist.
- An existing file larger than 10 MiB rotates before the next write, retaining `.1`, `.2`, `.3`. A record crossing the limit stays intact and rotates on a subsequent write; oversized records are not split. No fsync/crash-durability guarantee; filesystem failures are returned.
- Info logs every invocation. Decision logs exclude allow/passthrough records unless normalization errors, execution start errors, or hook failures are present. Normal child nonzero exit status alone is not a hook failure.
- Exec.Stdout/Exec.Stderr captured bodies are always omitted. Hook stderr, policy reasons, errors, diagnostics, argv, operations, and execution metadata are redacted.
- Content minimization is a separate log-only boundary: known prose flags/keys (`body`, `title`, `message`, `description`, `subject`, `commitHeadline`, `commitBody`, `comment`, `notes`) are always summarized as `[content: N bytes]`; other nested parameter/source strings and argv values use the Unicode-whitespace or >64-byte safety net. Structural repository/owner/branch/ref/URL/host/number/action/family values, flag names, command words and short enum-like values remain readable after credential redaction. API fields preserve keys, including nested field paths. Hooks keep their ordinary content.
- `Record.Source` is optional and contains the minimized normalizer source. GraphQL `query` values and `Source.GraphQL` are represented by `[graphql document: N bytes, sha256:<16 hex digits>]`. Counts/digests use original supplied bytes; the source document can already be capped by the normalizer. No rereading/reconstruction is performed.
- Wrapper diagnostics omit routine Global/Project config-source notes but retain ignored-project failures. When no enforcing policy/enabled pre-hook can act on API stdin, capture eligibility is unchanged and the log records `allow` plus `stdin not analyzed (nothing could act on it)`, preserving the unknown operation/errors. Explicit matched policy rules and hook denials retain their decisions.
- Invalid user config (or a forced project failure) logs `deny-invalid-config` when fail-closed, otherwise `passthrough-invalid-config`, plus error diagnostics at the default log path on every invocation. Fail-closed prints an error every time, exits 1, and never discovers/starts gh. Only fail-open stderr warnings are throttled, for ten minutes per exact failing config path/error pair. `<config-dir>/state/invalid-config-<sha256>.warning` contains a UTC RFC3339Nano timestamp, is opened without following symlinks/nonregular files, uses mode 0600, and is locked across processes; its directory is 0700. Any state I/O failure prints the warning. Invalid config never controls fallback logging.
- Maintenance: no generated logging metadata, regeneration command, upstream snapshot, or generator dependency exists. Curate prose/structural keys and argv flag overrides in `internal/logging/content.go`; add consumer-visible privacy cases in `content_test.go` and the pipeline e2e suite. Keep generic fallback, credential redaction, original-byte counts, and hook isolation intact.
- No stdout/stderr output. Integration must ignore logger failures for gh execution; it may print logger errors to stderr only when `GHOK_DEBUG=1`. The package returns errors and does not implement that CLI presentation policy.

## Verification and platforms

Config, redaction, and logger suites run hermetically with temporary fixtures. Logger tests exercise concurrent goroutines and pipe-synchronized subprocesses, including rotation without stale appends. Redaction has a learned-secret nonleak fuzz target and Result benchmark; logging has a Write benchmark. A throwaway executable exercised trusted config merging, immutable/redacted hook JSON, and credential-safe/no-capture JSONL through the public APIs, then was removed.

Project-trust scenarios include automatic policy, trust/edit/untrust, covered
byte/executable-bit changes, missing markers, identical worktree/clone content,
root/symlink containment, regular-file and manifest limits, external-command
exclusion, invalid stores, digest listing, current/all removal and permissions.
CLI/wrapper scenarios include hook revocation while policy remains active,
file-list/hook-ID output, coverage disclaimers and quiet wrapper trust notes.
These describe scenarios, not a gate-run report.

Config and redaction use platform-neutral Go APIs. Logging's descriptor, O_APPEND, O_NOFOLLOW, O_NONBLOCK, and flock code is Unix-build-tagged; macOS/Linux are the supported platforms. Tests were executed on macOS arm64. Linux amd64/arm64 cross-compilation is checked separately; Linux runtime execution remains the CI matrix's responsibility. Cooperating local-filesystem flock semantics are assumed; network-filesystem lock behavior is not guaranteed.
